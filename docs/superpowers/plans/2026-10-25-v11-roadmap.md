# Seafarer Budget 1.1 — дорожная карта сборки

> **For agentic workers:** this file is the index. Each stage has its own plan (`2026-10-25-v11-stage*.md`), written right before the stage starts, from the code the previous stage produced. Execute plans with superpowers:subagent-driven-development or superpowers:executing-plans.

**Goal:** выпустить 1.1.0 (телефон, ПК, бот, база) одним выпуском по спецификации.

**Spec:** `docs/superpowers/specs/2026-10-22-redesign-daily-budget-design.md` (утверждена 2026-10-25). Макет с итоговым интерфейсом (эталон для этапов 2–3): `seafarer-budget-preview.html`, опубликован https://claude.ai/artifact/LqtPifsFHbs7Tutu6JFTFK (версия 60).

## Правила на всю сборку

- Работа — в ветке `v1.1` (создаётся в начале этапа 0 от `main`). Ничего не пушится и не деплоится до этапа 7; живые бот и приложение 1.0 не трогаются.
- Секреты — только в `budget/.env` и `budget/bot.env`, используются через `node --env-file=…` / `supabase secrets set --env-file`, значения никогда не печатаются и не попадают в репозиторий и в чат. Chat id Маши — только в `bot.env`.
- Каждый этап заканчивается зелёными `npm test` и `npx tsc --noEmit`, коммиты маленькие, по задачам.
- Если реализация расходится со спецификацией (найдена ошибка или противоречие), спецификация правится тем же коммитом, с пометкой даты.

### Отступления от плана

- Файл миграции — `supabase/migrations/20261025120000_v11.sql`.
- Иконка категории в интерфейсе — новая колонка `glyph`; существующая `icon` по-прежнему хранит эмодзи бота.
- `deleted = true` — окончательное удаление; мягкое удаление использует `deleted_at` / `deleted_batch`.
- Клиенты шлют `base_rev`, серверный триггер сохраняет удаление против устаревших правок (в том числе от клиентов 1.0, которые возвращают `base_rev` равным null).
- Ответ push применяет серверные поля удаления.
- Зарезервированные деньги считают только движения живых и не архивных целей (`reservingGoalMoves`; архивная цель «не участвует в бюджете», §4).

### Перенесено на следующие этапы

- **Этап 2:** шторка записи ставит и снимает `document.documentElement.dataset.editing='1'` (условие для автообновления). Лимиты: строку из корзины (`deleted_at`) переиспользовать можно, строку с `deleted = true` — никогда (сделано); новые строки обязаны проставлять автора, источник и `created_at`. Архивные цели не резервируют деньги (§4) — сделано (`reservingGoalMoves`), экраны целей должны брать его же. `initDefaults` перезаписывает настройки и создаёт счета — мастер после «Удалить все данные» не может вызывать его как есть (счета и настройки остаются). `Record.tsx` сохраняет `category_id = null`, если категория записи в корзине, — при «Вернуть» категории запись остаётся без неё; решить (не трогать `category_id`, пока его не меняли). Настройки менять только через `repo.put('settings', …)`: он ведёт `_changed`, по которому синхронизация шлёт только изменённые поля.
- **Этап 4:** wipe/clear нужен фильтр по владельцу для Маши; `parser.ts` и `bot.ts` используют `alive()`; в `telegram-bot/store.ts` фильтры `.eq('deleted', false)` заменить на «живые» (ещё и `deleted_at is null`); `/undo` бота не должен выбирать строку из корзины; `keepalive_at`, `last_reminder_at`, `partner_seen_at` пишет только `service_role` (иначе `set_rev()` оставит старые значения); восстановление ботом ставит `base_rev = rev`; удаление счёта ботом окончательное, поэтому «Отменить» из спецификации после удаления счёта требует решения.
- **Этап 2 (остатки итоговой проверки, 2026-10-25):** `Home.tsx` меняет дату посадки через весь объект настроек (`{...settings, next_contract_date}`) — слать только `{id, next_contract_date}`, иначе устаревший снимок попадёт в `_changed`. В `csv.ts` поиск по `KIND_BY_LABEL` / `CURRENCY_WORDS` сделать через `Map` или `Object.hasOwn` (ячейка «constructor» сейчас даёт мусор). Импорт файла версии 1.0: переводы и обмены дают ошибку «Нет счёта «куда»» — показать понятное объяснение («в старом файле нет второй половины перевода — сверь баланс через «Сверка»»). Импорт перевода с неизвестным «Счёт куда» может стать переводом на тот же счёт — запретить или спросить.
- **Этап 6:** `resolvePendingRates` зовёт fx-rates на каждую дату — после большого импорта CSV (сотни дат) нужен пакетный запрос. Задачи сервера пишут `keepalive_at`, `last_reminder_at`, `partner_seen_at` только под ролью `service_role` (не `pg_cron` от `postgres` и не SECURITY DEFINER-функции — иначе правило 3 в `set_rev()` молча оставит старое значение). В миграции `coalesce(old_j -> 'deleted_rev', …)` — привести к `->>` как в правиле 2 (косметика). Окончательная очистка ставит `deleted = true` записям из корзины старше 24 ч.
- **Принято как есть:** ключ дубля для расходов/доходов не включает счёт (одинаковая трата на другом счёте скроет строку файла — редко); правка, сделанная во время отправки, повторно шлёт уже отправленные поля (последний пишущий выигрывает только по своим полям); устаревшее эхо из корзины может снова убрать восстановленную запись (замысел «удаление побеждает»).
